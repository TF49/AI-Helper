## 1. 发布及更新

### R01 · P1 · Tauri 签名格式解析错误，正常更新无法通过验签

位置：`src-tauri/src/update_trust.rs:232`，关键行 `237`；`scripts/package-release.ps1:47`、`74`、`88`。

`verify_minisign()` 将签名直接传给 `Signature::decode()`。Tauri 生成的 `.sig` 是整个 minisign 四行签名文本的 Base64 编码，而该解析器要求四行原始签名文本。脚本原样读取安装包 `.sig` 写进清单，并用 Tauri signer 生成清单 `.sig`，两个入口均有相同的不匹配。

结果：按当前脚本发布的合法清单首先会被拒绝；即使单独调整清单格式，安装包签名仍会被拒绝。这属于正常升级链路失效。

建议：统一签名编码协议，先进行 Base64 和 UTF-8 解码，再解析 minisign；使用真实 Tauri signer 生成的假数据签名覆盖成功路径、内容篡改和错误公钥场景。

依据：[Tauri CLI 2.8 签名实现](https://raw.githubusercontent.com/tauri-apps/tauri/tauri-cli-v2.8.0/crates/tauri-cli/src/helpers/updater_signature.rs)、[minisign-verify 解析实现](https://raw.githubusercontent.com/jedisct1/rust-minisign-verify/master/src/lib.rs)。此项已交叉核对上游源码，未在本机运行 Rust 验签程序。

### R02 · P1 · Windows 打包步骤没有清单签名所需的私钥

位置：`scripts/package-release.ps1:88`；`.github/workflows/release.yml:45`、`50`；`.github/workflows/update-release.yml:85`、`91`。

新脚本执行 `pnpm exec tauri signer sign latest.json`，但两套 workflow 仅在前一个 Build installer 步骤注入 `TAURI_SIGNING_PRIVATE_KEY` 和密码。Package release 步骤未注入，命令也未传入密钥参数。

步骤级环境变量不会延续到下一个步骤。按仓库当前 workflow 在干净 runner 上执行，清单签名无法取得私钥，随后缺失 `.sig` 的检查会使打包失败。

建议：在实际执行清单签名的步骤显式注入所需秘密，并检查签名命令退出码；执行一次完整的隔离发布演练。

### R03 · P1 · macOS 发布检查要求未生成的 DMG 签名，清单也缺平台条目

位置：`scripts/package-macos.sh:31`；`scripts/package-release.ps1:72`；`src-tauri/src/update_trust.rs:280`。

当前 Tauri 配置为 `createUpdaterArtifacts: true`。macOS 自动生成的更新签名对应 `.app.tar.gz`，脚本却强制要求 `.dmg.sig`；两套 workflow 均没有显式签署 DMG 的步骤。macOS 打包因此会退出，而发布 job 依赖 macOS 构建，影响整次发布。

此外，当前 `latest.json` 只生成 `windows-x86_64` 条目，后续发布仅收集文件，没有合并 Darwin 条目。即使修好 DMG 签名，macOS 客户端仍会因缺平台条目而拒绝更新。

建议：确定自定义更新器实际安装的产物，签署该产物；全部平台构建完成后合并清单，再签署最终清单。

依据：[Tauri 官方更新产物说明](https://v2.tauri.app/plugin/updater/#building)。未在本机执行 macOS 构建。

## 2. 凭据出口和配置

### R04 · P1 · Key 归属信息缺失时放宽限制，Bridge 出站也未统一执行策略

位置：`src-tauri/src/credential_policy.rs:10`、`30`、`52`；`src-tauri/src/accio/config.rs:113`、`126`；`src-tauri/src/accio/bridge.rs:1815`、`2338`。

第一处遗漏：`managed_keys.json` 缺失、损坏或不可读时直接使用空集合，保存失败也只记日志。旧版本升级没有来源迁移，登记依赖重新从云端取列表/明文。用户尚未重新取 Key，或持久化失败后重启时，既有 Bob Key 会被当成非受管 Key；保存、模型获取和握手路径对它只执行普通 HTTPS 校验，可以发往第三方 HTTPS 目标。

第二处遗漏：Accio 只在保存配置时校验目标。Bridge 加载旧配置后，LLM、embedding、生图在实际发送请求前没有再次执行目标校验。即使 Key 已登记为受管，升级前遗留的第三方地址或 HTTP 地址仍可收到 Key。禁止重定向不能替代首次目标校验。

建议：为来源状态建立版本和迁移流程，区分已验证自带 Key、受管 Key 与未知来源；元数据故障不能自动解除限制。在所有实际出站前执行统一策略，覆盖旧配置启动和后台刷新。

### R05 · P1 · Codex 保留旧 env_key，却把新 Key 写进另一个变量

位置：`src-tauri/src/codex.rs:165`、`176`、`262`。

局部合并只在 `env_key` 缺失时设为 `CUSTOM_OPENAI_API_KEY`，保存则始终只更新 `CUSTOM_OPENAI_API_KEY`。例如原配置引用 `THIRD_PARTY_API_KEY`，关联 Bob Key 后 URL 被修改，但凭据引用仍指向旧变量。目标地址检查只检查 URL，发现不了这个不一致。

结果：工具可能向新地址发送旧供应商凭据、使用错误 Key，或持续鉴权失败，界面却显示保存成功。

建议：同步更新本功能管理的凭据引用，或写入实际被引用的受控凭据位置；保存后联合校验最终目标和凭据引用。

### R06 · P1 · 安全文件写入未完整保护旧备份，权限失败也未阻止保存

位置：`src-tauri/src/safe_fs.rs:13`、`24`、`41`、`67`。

旧文件先复制到 `.bak`，备份不执行权限收紧。若升级前配置本来权限宽松，包含 Key 的旧副本仍可能维持宽松权限；给新临时文件加权限无法保护该备份。

临时文件先写入明文再设置权限，存在默认权限下的读取窗口。Windows 代码仅检查 `icacls` 是否成功启动，未检查进程退出码，设置 ACL 失败也会继续返回保存成功。Unix 设置权限的错误同样被忽略。

另外，替换采用“旧文件改名到备份→临时文件改名为正式文件”两步操作。两步之间崩溃会留下正式文件缺失状态，启动路径未见相应恢复机制；不满足文档所声称的崩溃安全原子替换。

建议：创建时即设置受限权限，保护旧副本并检查所有权限操作结果；使用平台原子替换原语并补恢复路径、同文件并发控制。权限故障和崩溃场景需要专项验证。

## 3. 预算及分组

### R07 · P1 · 预算持久化失败仍放行，损坏账本重置，多个进程可重复使用预算

位置：`src-tauri/src/paid_request.rs:67`、`82`、`91`、`106`；`src-tauri/src/accio/bridge.rs:590`。

`save_ledger()` 返回 `()`，仅记录落盘错误；`reserve_image_unit()` 因而仍返回成功并允许请求。重新启动时，读取失败或 JSON 损坏又被当成零消费、零预留。磁盘满、权限故障或替换期间崩溃都可能让已经使用或未决的额度丢失。

账本只在启动时加载，锁是进程内 `Mutex`，没有跨进程事务锁或单实例约束。将上限设为 1，先启动两个进程，两者都加载零消费；然后各请求一次，各自都能预留成功，即使两次操作完全顺序执行，也会产生两单。

现有名为 `concurrent_reserve_allows_only_budget_cap` 的测试只是对一个结构串行调用，未验证文件故障、崩溃或跨进程场景。

建议：加载、预留、持久化必须成为可失败的事务，落盘成功才允许发送；损坏状态应阻断受影响功能并进入恢复流程。使用跨进程锁/事务或唯一账本拥有者。

### R08 · P1 / 服务端依赖 · 改组仍然完整 GET→PUT，不能宣称只更新 group

位置：`src-tauri/src/auth.rs:1278`、`1288`。

删除“读取详情失败后按列表重建对象”的降级是正确修复。不过当前实现仍取完整详情、修改其中的 `group`，再将完整对象 PUT 回写，没有 ETag、版本条件或独立 group-only 接口。

具体场景：客户端读取旧详情后，用户在官网收紧 IP/额度/模型限制；随后客户端按旧详情切组。若服务端按完整 PUT 更新字段，新限制会被旧对象覆盖。线上是否接受这种覆盖，需要服务端接口证据确认。

建议：落实 group-only 或带版本条件的更新契约；依赖未就绪时限制改组功能。文档应明确“移除危险降级已完成，防并发覆盖待接口”，不能将本项标成客户端完全闭环。

### R09 · P2 · Token 编辑入口仍将未知费率当作 1 倍

位置：`src/components/auth/TokenSelectModal.tsx:404`、`464`、`1143`。

定价失败、尚在加载或目标倍率缺失时，`groupRatios[targetGroup] ?? 1.0` 使高倍率确认失效，提交按钮也使用相同默认值。回退获得分组名称没有提供权威倍率，仍可提交。已有其他 Token 的分组也会进入选项，所以不需要手工构造不存在的组名。

本地执行源码中的提交函数，令目标为另一分组、倍率表为空、未确认费率：模拟 `updateUserTokenGroup` 被调用 1 次，预期应为 0。

建议：统一两个改组入口，定价加载中、缺失、过期或非有限数值时禁止提交，并在重新打开/账号变化时清除旧费率。此项是用户主动改组的消费风险，不据此推断服务端越权。

## 4. 会话、前端及功能回退

### R10 · P2 · 钱包代次校验仅保护资料落盘，没有丢弃旧账号返回值

位置：`src-tauri/src/auth.rs:1617`、`1650`；`src/lib/useAuth.tsx:91`。

会话代次不匹配时，后端只跳过 role/email 更新，随后仍返回旧钱包；前端无条件 `setWallet(data)`。A 的响应头已收到、body 延迟期间退出并登录 B，旧响应随后返回时仍可能覆盖 B 的余额显示。

建议：对整个响应执行会话校验，过期结果返回明确错误；前端状态更新也绑定账号/请求代次。文档“代次不匹配直接丢弃响应”与现实现不符。

### R11 · P2 · 剪贴板清理定时器实际不会清理

位置：`src/lib/secureClipboard.ts:12`、`20`。

定时器启动异步 `readText()` 后，立即将共享 `expectedValue` 设为 `undefined`。Promise 恢复时，清理条件必然失败。

本地用支持正常读写的模拟剪贴板执行该源码，手动触发定时器并等待异步恢复：清空写入次数为 0，假 Key 仍留在剪贴板，预期写入次数为 1。

建议：在异步任务内保存本次待清理值和操作代次，等待清理完成后再释放相应状态，确保旧任务不会清除后来复制的内容。

### R12 · P2 · 新增 image_model 没有 UI 配置入口，普通保存会清空手工配置

位置：`src-tauri/src/accio/config.rs:29`、`89`；`src/components/AccioWorkPanel.tsx:252`；`src-tauri/src/accio/bridge.rs:2274`。

安全默认关闭未配置的生图通道合理。但后端 `image_model` 默认空，UI 返回结构、TypeScript 类型和保存 payload 都没有该字段。旧用户升级后没有 UI 启用方式；手工补字段后，普通 UI 保存又会因反序列化默认值将它清空。

建议：补显式配置与限制说明，并在更新其他字段时保留该字段；如本版有意停用生图，应在产品和发布说明中明确功能状态。

## 5. 文档还需要修正的状态

- SEC-09 计划要求的用户范围 DPAPI/Credential Manager 没有实现：`auth.rs:481` 仍将 refresh cookie、sid 序列化为长期 JSON。ACL 加固有价值，但不能据此将整个存储和迁移任务标为完成。
- `TokenSelectModal.tsx:221` 监听的 `ai_helper_auth_changed` 在当前 `src` 中没有发送者。`395` 的揭示 Key 请求也没有取消/代次校验，关闭时清空后，旧 Promise 仍可重新填入明文。
- `LoginModal.tsx:145` 的 2FA 分支只清 `password`，未清 `preparedLoginPayload` 和 ref；未启用 RSA 时其中仍可能保存原始密码。文档称进入 2FA 即清空全部载荷不准确。
- 当前生图预算每单始终预留/结算 `1`，默认总上限 `6`，没有可信价格、费率、有效期与服务端额度核验。它是本地次数约束，不能称为金额硬限；请求失败也直接结算，不是文档描述的完整未决状态机。
- `auth.rs:1641` 仍硬编码额度换算及 `1￥=4$`，SEC-08 的权威换算尚未落实。
- 图片取图在 `bridge.rs:2228` 预查 DNS，但实际请求重新解析，`2240` 的远端地址检查在请求发出后。应继续保留 DNS 绑定/重绑定防护未完成的状态，不能宣称 SSRF 全面闭环；是否能利用还受 TLS 和目标服务条件限制。
- 服务端 SEC-11/12 缺少对象授权、会话撤销、并发记账等证据的状态，文档保留为阻塞是合理的。本复核没有线上 Bob API 服务端实现，未验证这些控制。

## 6. 已有价值及建议验收顺序

应保留的改动包括：实例随机凭据和 body 前鉴权、监听失败中止启动、禁止计费未知时跨供应商重做、配置局部合并、损坏配置报错、禁重定向和远程 HTTPS 策略、指纹改摘要、清除编译期 Webhook、Actions 固定 SHA、禁止覆盖已发布资产。

建议先修 R01～R03 并验证“合法签名可以发布和更新”的完整成功路径；随后修凭据来源/出口、Codex 引用、文件存储和预算事务；再统一改组及会话响应隔离，补前端生命周期和兼容性验证。

结论文档应改成“部分整改完成，客户端仍有发布阻断及验收缺口”，为各任务列明实际代码、执行过的行为用例、平台和未完成项。测试数量与类型检查通过只能证明相应检查结果，不能证明所有安全规则成立。
